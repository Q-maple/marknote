为什么浏览器扩展的存储要按条拆开写

Manifest V3 的扩展把数据放在 chrome.storage.local 里，它本质上是一个键值对仓库。很多人在做划线类扩展时， 习惯把所有划线塞进一个数组，再整体读、整体写。数据量小的时候看不出问题，一旦划线超过几千条， 每次改动都要序列化整个数组，写入延迟会从几毫秒涨到几百毫秒，页面还会因为并发写入互相覆盖。

更稳的做法是一条划线一个键，比如 ann:<id>，内存里只保留一份 id 到划线的映射。 这样单次写入只动一条记录，耗时和数据总量无关；导出备份时把所有键读出来拼成一个数组即可， 导入时再按 id 去重合并，成本都在用户主动点击的那一下。

另一个容易被忽略的点是定位。网页的 DOM 随时可能被脚本改写，只存偏移量非常脆弱。 把「选中的文字 + 前后各 40 字上下文 + 虚拟文本偏移」一起存下来，还原时按由强到弱的顺序回退尝试， 才能在页面改版之后仍然把高亮找回来。

最后是容量：chrome.storage.local 默认只有 10MB，因为图片标记也会占用空间， 所以清单里必须声明 unlimitedStorage，否则用户划到一定量之后会遇到写入失败。
